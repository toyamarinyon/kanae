# EnkaからKanaeへ

- Status: 決定
- Date: 2026-07-12

## はじまり

Enkaは、左右のCommandキーを単独で押したときに、英数とかなを切り替えるために作りました。

- 左CommandのタップでJIS英数キーを送る
- 右CommandのタップでJISかなキーを送る

やりたいことが小さかったので、実装もそのまま小さく始まりました。左右のCommandキーと実行するアクションはデーモンのコードに直接書かれており、設定を考える必要もありませんでした。

この狭さは、Enkaを作った理由でもあります。汎用的なキーマッパーを作りたいわけではなく、自分が毎日使う二つの操作だけを、理解できる大きさで持っていたかったからです。

## 小さな例外が、二つのモデルを作った

バージョン0.2.0では `asciiInputRules` を追加しました。

きっかけは、herdrの `ctrl+q` のような操作です。かな入力中にターミナル上のコマンドを呼び出そうとすると、キー操作が日本語入力を経由して解釈されることがあります。そこで、特定のプロセスが動いているとき、指定したキー操作の直前に英数へ切り替えられるようにしました。

この機能自体は目的を果たしました。一方で、Enkaの中には二つの考え方が並ぶことになりました。

- 左右Commandの挙動はコードに埋め込まれている
- 追加の英数切替だけは設定ファイルに書かれている

どちらも実際にしていることは、キー操作を見つけて入力ソースを切り替えることです。それなのに、最初からあった挙動と後から追加した挙動が、別の仕組みとして扱われていました。

この違和感が、今回の変更の出発点です。

## すべてをbindingとして見る

次のバージョンでは、ハードコードされたCommandキーの挙動と `asciiInputRules` を廃止し、単一の `bindings` 設定へまとめることにしました。

一つのbindingは、次の三つを結びます。

1. `tap` または `press` のキージェスチャー
2. `ascii` または `kana` のアクション
3. 必要であれば、前面アプリケーション配下のプロセス条件

デフォルトの左右Commandも、特別なコードではなく設定として表現します。

```json
{
  "bindings": [
    {
      "trigger": { "gesture": "tap", "key": "left_cmd" },
      "action": "ascii"
    },
    {
      "trigger": { "gesture": "tap", "key": "right_cmd" },
      "action": "kana"
    }
  ]
}
```

この変更で、Enkaがしていることの全体が設定ファイルに見えるようになりました。利用者はEnkaがいつ介入するかを変えられますが、実行できるアクションは入力ソースの切替に限定したままです。

設定可能になったことよりも、もともと同じだったものを同じモデルで扱えるようになったことの方が、この変更では重要でした。

## Enkaという名前から少し外れてきた

実装が整理される一方で、Enkaという名前に少し違和感が出てきました。

Enkaは、左右Commandで英数とかなを切り替える最初の姿にはよく似合っていました。しかしbindingとして捉え直した後のアプリケーションは、特定の二つのCommandキーだけを扱うものではありません。小さな範囲ではありますが、キージェスチャーと状況を合図にして、適切な入力ソースへ切り替えるものになっています。

機能が無制限に広がったわけではありません。任意のキーへリマップしたり、コマンドを起動したりする予定もありません。それでも、最初の実装から付いた名前より、現在の境界を素直に受け止められる名前へ移る方がよいと考えました。

## Kanaeという名前

新しい名前は `kanae` にします。読みは「かなえ」です。

この名前には、いくつかの意味が重なっています。

- `kana` は、かな入力
- `e` は、英数（Eisu）
- 「かなえ」は、日本語の「叶え」に通じる
- 「叶える」という意味は、自分が大切にしている `ultrahope` のhopeともつながる

`ultrahope` の文字を直接組み込んだ名前も考えました。`bindhope`、`ulcue`、`cuepe` といった候補には、それぞれよい響きがありました。特に `cuepe` は小文字で並べたときの丸い字面が気に入っていました。

ただ、Kanaeは文字ではなく意味の方でhopeを受け継げます。同時に、かなと英数を扱うアプリケーションの機能も名前の中に残ります。機能と個人的な背景のどちらか一方へ寄せ切らず、その間に置ける名前だと感じました。

## リポジトリは歴史を引き継ぐ

Kanaeは新しいリポジトリへコードをコピーするのではなく、既存のEnkaリポジトリをrenameして続けます。

今回の変更は書き直しではありません。Enkaを使いながら感じた不都合と、そこから得た設計上の判断が、そのままKanaeにつながっています。コミット履歴を分断せずに残す方が、このアプリケーションがどう変わったのかを正直に示せます。

一方で、製品としての識別子は新しくします。

- CLIと実行ファイル
- アプリケーション名
- Bundle ID
- LaunchAgentのlabel
- インストール先
- 設定と状態ディレクトリ
- 配布URL

Kanaeとしての最初のリリースは `0.1.0` とし、タグはEnkaの既存タグと区別できる `kanae-v0.1.0` にします。Enkaの過去のリリースはリポジトリの履歴として残す方針です。

技術的な履歴は続いていても、利用者から見える製品には新しい境界を与える。その二つは、必ずしも同じタイミングで切り離す必要はないと思っています。

## いま残しておきたいこと

今回の改名は、機能が大きくなったからではありません。むしろ、何をしていて、何をしないのかが以前よりはっきりした結果です。

Enkaに例外として追加した機能を眺め直すと、それは最初の機能と同じ形をしていました。二つをbindingとしてまとめたことで、コードだけでなく、プロダクトの見え方も変わりました。

名前は最後に貼るラベルのようでいて、ときどき設計の理解がどこまで進んだかを映します。Kanaeという名前が、この小さな道具の境界をこれからも考えるための手がかりになればよいと思っています。

## ブログを書くときに掘り下げたい問い

- 例外として追加した機能が、実は元の機能と同じモデルだったと気づいた瞬間
- 設定可能にすることと、汎用ツールにすることの違い
- プロダクト名が実装の出発点に引っ張られること
- リポジトリの履歴を残しながら、製品として再出発する理由
- `kana + e` と「叶え」、そして `ultrahope` のhopeが重なった経緯
- 自分しか使っていない今だから、互換性より現在の設計を選べたこと
